# MURAS: публикация на Vercel

Подготовка задачи №16, 13 октября 2026 года. Исходная ветка — `main`,
merge-коммит — `cf5e0ed`. Этот документ описывает будущую публикацию:
в рамках подготовки деплой и отправка коммита на GitHub не выполняются.

## Настройки проекта

| Настройка | Значение |
| --- | --- |
| Git Repository | `diosdefin/Redbook` |
| Framework Preset | Vite |
| Production Branch | `main` |
| Root Directory | `./` (корень репозитория) |
| Install Command | `npm ci` |
| Build Command | `npm run build` |
| Output Directory | `dist` |
| Node.js Version | 22.x |

Framework, install/build commands и output закреплены в `vercel.json`.
Root Directory, подключение Git и Production Branch задаются в Vercel Dashboard.
Не указывайте `src`, `public` или `dist` как Root Directory. Проверенное локальное
окружение: Node.js 22.20.0, npm 11.12.1; lockfile хранится в репозитории.
Для текущей сборки не нужны Python, backend, база данных, секреты или env-переменные.

## Почему используются только два rewrite

`prebuild` валидирует локализацию, каталог, викторину и географию, генерирует
публичные JSON и копирует разрешённые фотографии. Vite собирает `dist/index.html`
и общие/раздельные JS/CSS. `postbuild` запускает `scripts/admin-entry.mjs`,
создающий **физический** `dist/admin/index.html` с теми же абсолютными путями assets.

`src/main.js` выбирает административное приложение по исходному адресу браузера
`/admin` или `/admin/`. Поэтому конфигурация содержит только:

```json
"rewrites": [
  { "source": "/admin", "destination": "/admin/index.html" },
  { "source": "/admin/", "destination": "/admin/index.html" }
]
```

Rewrite сохраняет адрес браузера. `/` обслуживается статическим `index.html`;
каталог, карта, урок, викторина и поддержка переключаются внутри публичного приложения.
`cleanUrls` и `trailingSlash` не включены: принудительная глобальная нормализация
адресов здесь не требуется. Используйте `/admin` или `/admin/`, а не
`/admin/index.html`: последний адрес не является клиентским маршрутом админки.

Нет catch-all, SPA fallback или rewrite для assets. Существующие JS, CSS, SVG,
WebP, JSON и `robots.txt` должны отдаваться как файлы, отсутствующие — с HTTP 404.
Не добавляйте из универсальных инструкций Vite правило `/(.*) → /index.html`.
Локальный `vite preview` может возвращать SPA HTML для отсутствующих адресов;
он не проверяет маршрутизацию Vercel. Проверка реальных HTTP-ответов после деплоя
обязательна; локальная проверка сборки не заменяет её.

Документация: [конфигурация и rewrites](https://vercel.com/docs/project-configuration/vercel-json#rewrites),
[Vite на Vercel](https://vercel.com/docs/frameworks/frontend/vite).

## Первая публикация — действия владельца после отдельного согласования

1. Проверить подготовленный коммит и разрешить его отправку. Затем отправить
   `main` в существующий [GitHub-репозиторий](https://github.com/diosdefin/Redbook).
   Здесь эта отправка не выполнялась. Не использовать force push.
2. В Vercel выбрать **Add New → Project**, подключить GitHub через официальное
   приложение Vercel и предоставить доступ к `diosdefin/Redbook`.
   Если репозиторий не виден, проверить доступ приложения в GitHub → Settings →
   Applications → Installed GitHub Apps → Vercel → Configure.
3. Импортировать этот репозиторий. Установить значения таблицы выше; проверить,
   что `vercel.json` присутствует именно в импортируемом коммите.
4. Проверить GitHub default branch — `main` и выбранную Production Branch — `main`.
   После создания проекта проверить Vercel → Settings → Environments → Production
   → Branch Tracking. В интерфейсах с разделом Git настройка может называться
   Production Branch. Не назначать `competition-v1` или WIP-ветку для Production.
5. В Settings → Build and Deployment проверить Node.js 22.x и команды. Не менять
   Build Command на `vite build`: это пропустит npm `prebuild` и `postbuild`.
6. Нажать **Deploy**, дождаться состояния Ready. В build log должны завершиться
   валидация, Vite и `postbuild` с генерацией административной страницы.
   Тесты автоматически не входят в `npm run build`: выполнить `npm test` до
   публикации или отдельно настроить проверку в существующем процессе GitHub.
7. Открыть адрес, реально выданный Vercel, и пройти проверки ниже. Проект не содержит
   вымышленного домена, URL соцсетей или требования подключить собственный домен.

После подключения Git новые коммиты в Production Branch могут автоматически
запускать production-деплой. Изменения других веток/PR обычно создают Preview.
Проверяйте выбранный commit SHA и Environment каждого деплоя.
Инструкция подключения: [Vercel for GitHub](https://vercel.com/docs/git/vercel-for-github);
[настройки сборки](https://vercel.com/docs/builds/configure-a-build).

## Приёмка опубликованной версии

- Открыть `/` в чистом профиле: начальный язык KY, бренд MURAS. Переключить RU/EN,
  проверить поиск, фильтры, девять карточек, источники и лицензии, карту, викторину,
  урок, визуализацию и демонстрационную поддержку. Обновить страницу.
- Ввести `/admin` и `/admin/` непосредственно в адресной строке, обновить каждый
  адрес. Должна открываться Muras Admin, с отдельной серой дизайн-системой.
  Проверить локальный импорт/экспорт по `docs/manual-qa-checklist.md`, используя
  копию источника. Публичный каталог после редактирования не должен измениться.
- В DevTools Network: проверить HTTP 200 и правильный Content-Type для реально
  сгенерированных `/assets/*.js`, `/assets/*.css`, `/favicon.svg`, `/robots.txt`,
  `/images/placeholder.svg`, всех девяти `/images/approved/*.webp`,
  `/data/species.json`, `/data/quiz.json` и `/data/geography/*`.
- Проверить **несуществующие** `/assets/missing.js`, `/assets/missing.css`,
  `/missing.svg`, `/images/missing.webp`, `/data/missing.json`, `/missing/robots.txt`:
  ожидается 404, а не успешный HTML-ответ. Наличие HTML в теле страницы ошибки 404
  допустимо; подмена ресурса главной страницей со статусом 200 — нет.
- `/data/species.source.json`, `/data/backups/`, `/data/archive/`, `/src/`,
  `/scripts/`, `/package.json` не должны выдавать внутренние файлы проекта.
  Не публиковать корень репозитория вместо `dist`.
- Проверить Console: нет ошибок загрузки модулей, JSON или изображений.
- Проверить ширины 320, 375, 768, 1024, 1440 и 1920 px: меню, карточку/диалог,
  ползунок, карту и /admin. Затем реальный телефон; проверить касание, Tab, Escape,
  возврат фокуса и горизонтальное переполнение. Подробная инструкция:
  [ручная QA-проверка](manual-qa-checklist.md).

## Данные, Windows и безопасная публикация

Генератор уже детерминирован: JSON записывается UTF-8 с LF, без времени генерации.
На Windows `core.autocrlf=true` ранее создавал ложные modified-состояния после
записи LF; проверенные семь generated JSON/GeoJSON побайтно совпали с `HEAD`.
`.gitattributes` закрепляет `text eol=lf` только для generated JSON/GeoJSON.
Глобальные настройки Git, исходная научная база, исторические резервные копии и
фингерпринтированные upstream-файлы не меняются. Генератор переписывать не нужно.

Перед следующей публикацией:

```powershell
npm ci
npm test
npm run data
npm run data:validate
npm run build
git status --short
git diff --stat
```

Сравнивать результаты повторной генерации; не коммитить JSON лишь ради LF/CRLF.
Содержательные изменения данных должны проходить научную редактуру отдельно.

В `dist` попадают публичные проекции и только лицензированные изображения,
а не полный `data/species.source.json`, demoArchive или резервные копии.
Публичные проекции содержат необходимые источники, лицензии и географические
свидетельства: они предназначены для публикации и не являются внутренним источником.

Админка — **доступный локальный редактор**, без авторизации и серверного сохранения.
`robots.txt` содержит `Disallow: /admin`, что не является защитой доступа.
Она хранит черновики в браузере и скачивает экспорт; опубликованные JSON напрямую
не меняет. Изменение каталога требует ручного переноса проверенного экспорта в
репозиторий, генерации, тестов и нового деплоя. Не загружать секреты или личные
данные в редактор и не объявлять его защищённым серверным CMS.
Данные localStorage привязаны к origin: localhost, Preview и Production имеют
разные локальные черновики/настройки. Существующие ключи не изменены.

## Откат

При неудачной сборке не продвигать её в Production; ранее успешная публикация
остаётся доступной. Если Ready-деплой уже стал Production и содержит регрессию:

1. Открыть проект → Production Deployment → **Instant Rollback** (или меню
   нужной записи на Deployments). Выбрать предыдущий исправный production-деплой,
   проверить адреса и SHA, подтвердить откат.
2. Повторить проверки `/`, `/admin`, ресурсов и данных. На первой публикации
   предыдущего production-деплоя ещё нет; откат к нему невозможен.
3. Исправить код отдельным коммитом или `git revert` через обычный review-процесс.
   Не переписывать историю `main` и не использовать force push.
4. После проверки исправленной сборки использовать **Undo Rollback** с выбором
   исправного деплоя. Instant Rollback отключает автоматическое назначение
   production-доменов; Undo Rollback восстанавливает его. Доступные варианты
   отката зависят от плана и полномочий пользователя.

Откат Vercel меняет назначение deployment, не откатывает Git и не изменяет
пользовательский localStorage. Основание:
[официальная инструкция Instant Rollback](https://vercel.com/docs/instant-rollback).

ресурсы перечисленных типов не совпадают с ними. Реальный Vercel deployment,

в этой задаче не выполнялась; соответствующий чек-лист приведён выше.
Vue-компоненты, маршрутизирующий entry, данные, лицензии и дизайн не изменены.
