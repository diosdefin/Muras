## Реализованная модель

Старый контракт `Species.population`, `validatePopulation`, `populationPresentation` и научный gate `reviewStatus: approved` **не изменены**. Добавлен отдельный типизированный JSON sidecar:

- `identity`: точные speciesId, принятое имя, SPECIES/SUBSPECIES и только уже сохранённые taxon IDs. Пустые прежние наборы ID не заполнены выдуманными значениями.
- `estimate`: exact/approximate/range, value/min/max, единица, территория и scope, **year либо observationPeriod**, отдельный publicationYear, метод, confidenceInterval/uncertaintyInterval. Диапазон не превращается в среднее.
- `source` и `documentation`: URL первоисточника, страница/раздел, название из источника, статус подтверждения, ссылка на архивную копию при наличии, хеш исходного свидетельства и ограничения.
- `scientificReviewStatus: pending`, `verified: false`, `lastReviewedAt: null` остаются научным состоянием новой оценки.
- `populationPublicationStatus` выражает редакционное состояние: подготовленный кандидат unpublished, отдельное решение authorized либо revoked. Научный статус не используется для автоматической выдачи редакционного разрешения.

Новый `src/data/population-publication.js` проверяет контракт и SHA-256 через Web Crypto; единый адаптер формирует текст для KY/UZ/RU/EN и существующей визуализации. `usePopulationPresentation` выбирает этот режим только при явно переданном контексте; иначе используется старый адаптер. На изменении/отзыве контекста прежнее число синхронно скрывается, а generation token не позволяет позднему async результату вернуть устаревшее разрешение. Снимок данных делается до await. Отсутствие Web Crypto даёт unknown.

`App` принимает необязательный `populationPublicationRelease` от доверенного host/API, строит соответствия ID → контекст и передаёт его существующим modal/page. Это отдельный sidecar: поля карточек не сливаются и не перезаписываются. По умолчанию prop отсутствует; нет новой автоматической сетевой загрузки, публикационного флага в карточках или Canvas на каждой карточке списка. Подготовленный пакет с null-разрешением остаётся скрытым даже при передаче в App.

Реализованы информационные строки периода, отличающегося года публикации, отдельного ДИ, источника/страницы, архивной копии и предупреждения «По опубликованному источнику, независимая проверка MURAS ожидается». Это новые данные внутри существующего блока; CSS, глобальные стили, расположение компонентов, дизайн, карта и образовательные функции сохранены. Старые переводы не переписаны, добавлены 14 ключей на каждом языке.

## Явное редакционное разрешение

Для показа требуется **отдельное решение** доверенного слоя публикации, а не поле, самостоятельно выставленное кандидатом. Валидируются schemaVersion, ownerRole=project_owner, decisionId, фактическая календарная date без будущего значения, reason, populationPublicationStatus=authorized, точный packetFingerprint и список authorizedCandidates с ID и candidateFingerprint.

Решение привязано к хешу manifest выбранных оценок, а manifest — к их индивидуальным хешам и прежнему исследовательскому registry. Wildcard, повтор ID, другой manifest, подмена источника/числа, неправильные имя/ранг/GBIF, неподтверждённая территория, NEEDS_EVIDENCE или отозванный/отсутствующий допуск дают unknown. Даже заново подписанный **синтетическим тестовым решением** NEEDS_EVIDENCE блокируется валидатором. Разрешение может явно перечислять подмножество фиксированного набора, но не новые записи вне него.

**Граница доверия:** SHA-256 проверяет целостность, не личность человека. Этот клиентский gate не является серверной аутентификацией, электронной подписью или хранилищем решений. Перед реальной публикацией доверенный host/защищённый workflow должен получить явное распоряжение владельца, сохранить проверяемую запись решения и подать её актуальную версию. Поле ownerRole в произвольном недоверенном JSON само по себе не доказывает полномочия. В этой задаче реального решения, его файла, публичного release-sidecar и mass apply не создавалось.

Отзыв/удаление решения в переданном контексте немедленно убирает число и освобождает Canvas/RAF; pending-оценка не становится approved. Доставка серверного отзыва в уже открытый клиент относится к будущему доверенному transport-слою; фонового polling и backend в этой задаче нет.

## Визуализация и ограничения источников

Используются прежние SpeciesVisualization, PopulationInfo, Canvas/CSS engine и requestAnimationFrame lifecycle. Фотография изначально цветная; эффект запускается кнопкой. Для отдельно разрешённой документированной оценки используется **символическая** пикселизация; клетки не означают число особей. `populationCells` для нового pending-режима не строит буквальные индивидуальные отметки. Без пригодного разрешения — CSS grayscale; placeholder не пикселизируется. У отдельно разрешённой оценки без фото метаданные доступны под placeholder при отключённой кнопке эффекта; отзыв скрывает их и там. Сохраняются восстановление фото, сброс на смене вида/оценки, reduced-motion, offscreen pause и cleanup.

Ограничения не сняты редакционным решением: исторические годы не стали современными; локальные участки не стали всей страной; целочисленные оценки не стали exact; диапазоны не усреднены; ДИ не назван количеством особей; отсутствие встреч не стало нулём. Научная независимая проверка остаётся pending.
