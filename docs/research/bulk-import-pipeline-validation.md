## Архитектура

- `scripts/bulk-pipeline.mjs` — единый CLI, блокировка реестра, контрольные точки,
  отчёты, явное одобрение редактора и применение одобренных партий.
- `scripts/lib/research-pipeline.mjs` — формат реестра, CSV, научные проверки,
  индексы таксонов, состояния, отпечатки материалов и планирование партий.
- `scripts/lib/local-research-adapter.mjs` — только чтение локального JSON/материалов,
  SHA-256, ограничения путей, проверка лицензий и локальных фото. Сетевого кода нет.
- Существующие `planBatchImport`, `validateSpecies`, `validateSource`, `inspectAssets`
  остаются финальными проверками. Импортёр продолжает только добавлять записи,
  не перезаписывая каталог; сохраняет проверки ID/таксона/вида-подвида, backup и идемпотентность.
- В список `IMPORT_BRANCHES` добавлена `feature/bulk-import`; `main` остаётся запрещённой.
  В `importBatchFile` добавлен необязательный `expectedBatchSha256`: конвейер проверяет
  точные байты одобренного пакета перед применением, защищая от подмены промежуточного файла.

Источник каталога читается один раз для планирования. Используются единый индекс
существующих ID/имён/таксономических ID и индекс конфликтов всего реестра, включая
конфликты между разными партиями. Размер реестра — до 200, размер партии — 1–25,
по умолчанию 25. Отклоняются также имена/ID из архива.

Адаптер кеширует чтение одного и того же локального материала в пределах запуска.
Кеш не переносится в следующий процесс. Диагностика из реестра не служит разрешением
пропустить проверку: `check`, `approve`, `resume`, `apply` повторяют строгую валидацию.
Перед каждой записью импортёр заново читает актуальный каталог и проверяет весь план.
Это сохраняет безопасность при обновлённом каталоге и изменённых фотографиях.

## Вход и формат исследовательского реестра

Вход JSON: массив кандидатов или объект с массивом `candidates`. CSV: заголовок
с колонками `id`, `originalScientificName` и необходимыми дополнительными полями.
CSV читается в UTF-8 (допустим BOM), поддерживает кавычки, запятые внутри полей,
удвоенные кавычки, CRLF и переносы внутри кавычек. Некорректный CSV/UTF-8 отклоняется.

Колонки `nationalRedBook`, `countryOccurrence`, `taxonomyEvidence`, `taxonomySourceIds`,
`sources`, `contradictions`, `missingData`, `materials`, `draft` содержат JSON в CSV-поле.
Пустые значения этих колонок становятся отсутствующими сведениями, а не утверждениями.
Пути `draftFile` передаются обычными строками. Значения не исполняются как код.

`init` создаёт документ:

```json
{
  "schemaVersion": 1,
  "documentType": "bulk-research-registry",
  "registryId": "research-queue",
  "batchSize": 25,
  "candidates": []
}
```

Поля каждого кандидата:

| Поле | Содержание |
|---|---|
| `id` | Уникальный безопасный slug; отсутствие/повтор ID делает вход неоднозначным и отменяет создание реестра |
| `originalScientificName` | Исходное научное имя, без автоматического исправления |
| `acceptedScientificName` | Принятое имя из источника, до исследования `null` |
| `rank`, `group` | SPECIES/SUBSPECIES и группа из действующей модели |
| `nationalRedBook` | `listed`, `category`, `edition`, `year`, `sourceIds`, `basis`, `claimsCurrentLegalStatus` |
| `countryOccurrence` | `countryCode: KG`, `confirmed: true`, `sourceIds`; до подтверждения `null` |
| `taxonomyEvidence` | `canonicalName`, `rank`, `status: ACCEPTED`, `matchType: EXACT`, `taxonId`, `sourceId` |
| `taxonomySourceIds` | ID источников, подтверждающих научное имя |
| `sources` | Реальные title/publisher/URL/accessedAt, уникальные ID, `supports`, при необходимости taxonId |
| `contradictions` | Список нерешённых противоречий |
| `missingData` | Список обязательных научных пробелов, блокирующих допуск |
| `materials` | Список локальных снимков `{path, sha256}`; при наличии проверяется каждый файл |
| `draft` или `draftFile` | Готовящийся объект вида по текущей модели, inline или отдельный локальный JSON; только один вариант |
| `state` | Текущее рабочее состояние |
| `approval` | Явное решение редактора с отпечатком проверенных данных; при `init` всегда `null` |
| `rejectionReason` | Явная причина редакторского отклонения, если есть |
| `diagnostics`, `checkedFingerprint`, `importedFingerprint` | Служебные результаты и контрольные точки |

`init` игнорирует входные состояния, решения и контрольные точки: каждый кандидат
начинает как `pending`. Создание уже существующего реестра запрещено (`wx`), поэтому
повторный `init` не теряет исследования или одобрения. Для нового списка создайте
отдельный реестр; для продолжения используйте `resume`.

## Научный допуск

Нужны связанные источники национального включения, встречаемости KG и точного
принятого таксона. ID таксона должен происходить из источника, поддерживать
`scientificName` и соответствовать `taxonomyEvidence`; поддерживаются существующие
контракты `gbif:`/`iucn-gbif:`. Неизвестный идентификатор не создаётся автоматически.
Для будущего другого таксономического адаптера потребуется явное расширение контракта
импортёра и тестов; произвольные ID не принимаются.

`basis: historical_edition` требует `claimsCurrentLegalStatus: false` и явного
обозначения исторической записи в `edition` карточки. Исторический источник 2006 года
не становится утверждением о действующем правовом перечне. Для `current_legal_list`
нужны `claimsCurrentLegalStatus: true` и источники с отдельным
`supports: nationalRedBook.currentLegalStatus`; исторически обозначенный документ
для этого не принимается. Подлинность, соответствие очерка таксону и актуальность
юридического документа проверяет редактор по локальным материалам.

В черновике должны сохраняться национальные сведения и соответствующие источники
реестра, а источники встречаемости должны быть связаны с регионом KG.
Нерешённые `contradictions`/`missingData` блокируют подготовку к импорту.
Без `draft` сохраняется исследовательская очередь, полноценная карточка не создаётся.
Сведения, тексты, `sources.supports`, регионы и оценки IUCN не генерируются по шаблону.

У отсутствующих полей черновика только безопасные defaults: `verified:false`,
`lastReviewedAt:null`, `UNKNOWN_POPULATION`. Предоставленное `verified:true`
отклоняется. Проверка численности остаётся `pending`; этот конвейер не предоставляет
её независимое одобрение. Доказанные оценки можно передать с поддерживающими
источниками по модели, но их научная проверка проводится отдельным существующим процессом.

## Жизненный цикл

| Состояние | Значение и следующий шаг |
|---|---|
| `pending` | Импортирован список, исследование ещё не запускалось |
| `needs_evidence` | Нет подтверждений, есть обязательные пробелы/противоречия либо ошибка локальных материалов |
| `research_ready` | Научные сведения собраны, но публикационный черновик отсутствует или не прошёл техническую проверку |
| `needs_photo` | Фото не имеет допустимого технического/лицензионного допуска; исправить, заменить или убрать в пользу placeholder |
| `ready_for_review` | Научные и технические проверки пройдены, требуется явное решение редактора |
| `approved_for_import` | Редактор одобрил конкретное содержимое, отпечаток актуален |
| `imported` | Импортёр успешно добавил запись; идентичная повторная запись ничего не меняет |
| `rejected` | Дубликат/конфликт или редакторское отклонение с причиной в diagnostics/rejectionReason |

Отсутствующее фото отражается как `readiness.photo: placeholder` и не блокирует
`ready_for_review`, поскольку модель разрешает пустой `images`. Статус `needs_photo`
нужен, когда переданное фото требуется исправить или заменить. Отчёт отдельно
показывает `photoCheck`, наличие коротких/полных текстов каждого языка,
`missingNames`, `translationRequired` и `scientificReviewRequired`.
Непереведённые научные тексты остаются с fallback; неизвестные народные названия — `null`.

Локальные WebP проверяются существующим инспектором (контейнер, размеры, SHA-256,
EXIF/XMP), моделью метаданных и дополнительным соответствием лицензии её URL.
Для Apache проверяются локальные LICENSE/NOTICE и их суммы. Неизвестные лицензии
требуют отдельного допуска. Сам адаптер не подтверждает личность автора или
определение организма по пикселям — это часть редакторского просмотра.

`approve` требует одного `--candidate`, имени редактора, даты и причины.
Одобрение связано SHA-256 с исследованием, черновиком и локальными материалами;
изменение любого из них делает решение устаревшим. `state` сам по себе не даёт права
на запись. Редакторское решение об импорте не устанавливает `verified:true`.

## Точные команды PowerShell

Входной файл `data/research/incoming-candidates.json` или `.csv` готовит редактор
с проверяемыми локальными сведениями. Эти будущие файлы в текущую задачу не добавлены.

```powershell
Set-Location 'C:\Users\Asus\Desktop\Redbook'
node scripts/bulk-pipeline.mjs --help
$registry = 'data/research/bulk-candidates.registry.json'

# Создать новый реестр (до 200 строк), партии по 25.
npm run data:bulk:prepare -- --input data/research/incoming-candidates.json --registry $registry --id bulk-candidates --batch-size 25
# Альтернатива: CSV вместо JSON, для нового реестра.
# npm run data:bulk:prepare -- --input data/research/incoming-candidates.csv --registry $registry --id bulk-candidates --batch-size 20

# Только просмотр: реестр, каталог и материалы не изменяются.
npm run data:bulk:check -- --registry $registry
npm run data:bulk:check -- --registry $registry --batch 1
# Явно сохранить отдельный отчёт в игнорируемую служебную директорию.
npm run data:bulk:report -- --registry $registry --report .generated/bulk-candidates-report.json

# Сохранить состояния, черновики партий и отчёт; продолжить после перерыва.
npm run data:bulk:resume -- --registry $registry

# Только после фактического редакторского просмотра конкретного кандидата.
# Заменить candidate-id, имя, дату и причину реальными значениями.
npm run data:bulk:approve -- --registry $registry --candidate candidate-id --reviewer 'Имя редактора' --date '2026-10-14' --reason 'Проверены источники и соответствие таксона'
npm run data:bulk:reject -- --registry $registry --candidate candidate-id --reason 'Причина отклонения'

# Импортировать только одобренную и вновь проверенную первую партию.
npm run data:bulk:apply -- --registry $registry --batch 1
# Или все одобренные партии реестра.
npm run data:bulk:apply -- --registry $registry

npm test
npm run data
npm run data:validate
npm run build
```

Команды `check` и `report` без `--report` выводят JSON только в stdout и ничего
не сохраняют. Наличие отклонённых записей означает exit code 2; технический сбой
CLI — 1; отложенные записи отражаются в отчёте, их наличие само по себе — не ошибка CLI.
Для машинной обработки смотрите `counts` и `states`, а не только код процесса.

`resume` сохраняет `.generated/bulk-pipeline/<registryId>/batch-N.json` после каждой
партии и атомарно обновляет диагностику в реестре. Черновик имеет
`documentType: research-draft-batch`, поэтому исходный импортёр не примет его за
публикационный пакет. Только `apply` формирует `species-import-batch` из актуально
одобренных записей. Отчёт сохраняется в той же директории как `report.json`.

Каталог получает точный backup до изменения:
`.generated/import-backups/<batchId>-<sourceSha256-prefix>.json`.
Работают блокировка каталога, проверка конкурентного изменения, временный файл
и rename существующего импортёра. При ошибке одной записи остальные результаты
сохраняются; импортируются только допустимые одобренные записи.

Реестр блокируется отдельным `.pipeline.lock`. Чужой lock или временный файл
не удаляется автоматически. После аварийного завершения процесса, когда `finally`
не смог выполниться, сначала убедитесь, что процесс завершён, затем удалите только
оставшийся lock выбранного реестра через `Remove-Item -LiteralPath` и повторите
`resume`/`apply`. Не удаляйте блокировку работающего процесса. Если завершение
произошло между rename каталога и сохранением реестра, `apply` восстанавливает
`imported` только при совпадении одобренного отпечатка, полной идентичности записи
и повторной строгой проверке; дополнительная запись не появляется.

## Ограничения

Конвейер не ищет источники, не загружает фото, не переводит тексты, не определяет
организмы по фото и не устанавливает текущий юридический статус самостоятельно.
Адаптер принимает только локальные проверяемые материалы; GBIF/Commons можно
подключить позже через явно запускаемый сборщик снимков с последующим просмотром.
Лимит каждого локального JSON/материала — 16 MiB. Пути ограничены проектом,
включая symlink/junction; отчёты и пакеты пишутся только в `.generated`, реестр —
только в `data/research/*.json`. Небезопасные JSON-ключи отклоняются.

Одобрение — локальный редакторский протокол, не криптографическая подпись и не
аутентификация личности; репозиторий и реестр должны контролироваться редакторами.
Старые команды подготовки/фото/импорта сохраняются для совместимости и используют
свой прежний процесс. Для нового массового реестра применяется `data:bulk:apply`,
который требует явное актуальное одобрение и полную валидацию.

Merge, push и deployment не выполняются.

## Отдельное разрешение предварительной публикации — задача 22.5B

По явному решению владельца от 14.10.2026 добавлен `data:bulk:provisional`.
Он не вызывает `approve`, не заполняет `approval.reviewer` и не создаёт научного
одобрения. Прежние `approve/apply` и их проверки сохраняются. Новая запись имеет
`publication.status:provisional`, `scientificReviewStatus:pending`,
`independentReviewer:null`, `verified:false`, `lastReviewedAt:null` и проверку
численности `pending`. Интерфейс использует существующую отметку о необходимости
редакторской проверки; статус не означает подтверждённый актуальный национальный статус.

Разрешение относится только к точному manifest (1–25 записей), его SHA-256,
fingerprint реестра и fingerprint/хешам каждого черновика. Нерешённые научные
противоречия, missingData, конфликты с каталогом/архивом и ошибки источников,
таксономии, структуры, изображений/лицензий блокируют и этот режим.
Пакет применяется существующим импортёром одной операцией с `requireAllValid:true`:
если повторная проверка любой записи не проходит, каталог не записывается.

Все параметры обязательны, включая `--mode dry-run|apply`, реальную дату,
роль `project_owner`, уникальный `--decision-id` и основание с явным разрешением.
Имя владельца или независимого редактора не выдумывается. Перед применением
сохраняется неизменяемый журнал решения в `data/research/publication-decisions/`.
Это локальный протокол разрешения, не криптографическая подпись и не удостоверение
личности. Журнал отражает разрешение; факт применения отдельно отражён в отчёте
конвейера и метаданных опубликованных записей. Если процесс прерван, повтор с тем
же решением безопасен; чужие lock не удаляются. Повторное решение с тем же ID и
другими материалами/основанием отклоняется. Старые разрешения не действуют для
следующих пакетов: нужен отдельный запрос владельца, новый manifest и новый ID.

```powershell
# Шаблон для отдельно разрешённого следующего пакета — не готовое разрешение.
npm run data:bulk:provisional -- --registry data/research/queue.json --manifest data/research/review.json --mode dry-run --owner-role project_owner --decision-id UNIQUE-ID --date YYYY-MM-DD --reason "ФАКТИЧЕСКОЕ ЯВНОЕ РАЗРЕШЕНИЕ ВЛАДЕЛЬЦА НА ЭТОТ ПАКЕТ"
# Только после успешного dry-run и явного разрешения на этот же пакет:
npm run data:bulk:provisional -- --registry data/research/queue.json --manifest data/research/review.json --mode apply --owner-role project_owner --decision-id UNIQUE-ID --date YYYY-MM-DD --reason "ТО ЖЕ ОСНОВАНИЕ"
```

В исследовательских черновиках ничего не меняется. `check` распознаёт уже
предварительно опубликованную запись только при совпадении научных данных и
актуального researchFingerprint, продолжая все проверки и возвращая `imported`.
Это не `approved_for_import`. Изменение научных данных или подмена метаданных
не разрешает перезапись: существующий append-only импортёр отвергает конфликт.
